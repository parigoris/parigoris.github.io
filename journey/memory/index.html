Chapter 4 · Memory

My AI invented a mistake for me

Every session starts with a blank memory, so mine lives in files. Where a fact was missing, a helper agent filled the gap with a story that never happened, and I published it. Here’s how my files work now.

27 November 2026 · 6 min read

The 30-second version

  • A session, or a helper agent, only knows what’s in its context. When the session ends, that’s gone.
  • Ask an AI to write about something it can’t see, and it tends to fill the gap with something plausible. Mine invented a mistake, and it went live on this site.
  • So memory lives in files in the repository: rules, a task board, handoff notes and logs. Anything a chat remembers about GitHub gets checked again before it’s used.

On 26 November I found a mistake on my own website that I had never made.

Chapter 1 had a “My mistake” box that said “I expected Claude to remember yesterday”, and a card on the home page said it too. It sounded right, because most beginners make that mistake. But nothing like it was in my logs. A helper agent writing the chapter had written a believable mistake instead of a real one from my files. I read it and merged it.

Nothing about the text looked wrong, and that was the problem. The rule I made that day only covered new boxes. On 27 November an editor agent checked the old ones and found a second invented story, in chapter 2, about building this whole website in one chat. That one was live too, and it’s gone now.

The model only knows what it can see

Context
= everything the model can see right nowYour messages, the chat so far, and every file it has opened in this session. When the session ends, the context goes with it.

A new session knows nothing about yesterday. A helper agent knows even less, because it starts with only the task you hand it. What I hadn’t expected was what happens at the edge of the context. Ask an AI to write about something it can’t see, and it rarely stops to say so. It writes what usually happens, and what usually happens reads exactly like the truth.

So memory needs two things: the facts have to sit where every session will find them, and “it’s in the file” has to be the only proof that counts.

Memory lives in files

My home base is a private repository called hq. It has four kinds of memory, and each one answers a question a new session would otherwise have to ask me.

File The question it answers When it’s read
CLAUDE.md How do we work here? Automatically, at the start of every session
plans/board.md Who’s doing what, and what’s finished? Before any new job, so nothing is done twice
handoffs/ Where did we stop? In the first message of a new session
logs/ What happened, and what did we decide? Before writing anything that claims a fact

The logs are three plain files with one line per entry. The mistakes log holds what went wrong and the rule that followed. The security log records every access I grant or refuse, and the learning log gets one line per session. They’re dull to write, and they’re the only reason this chapter can give you dates.

CLAUDE.md is the only one of these that Claude Code loads by itself (how Claude remembers your project). The others work because CLAUDE.md tells the agent when to read them, and because they live in the repository, which every session copies in. Chapter 1 has that setup.

My mistake26 Nov 2026

A helper agent made up my mistake, and I published it

Every chapter needs a “My mistake” box. The helper agent writing chapter 1 didn’t take one from my mistakes log. It wrote the mistake most beginners make, because that’s what usually happens. I didn’t check it against my logs either. The box has since been replaced with a real, logged mistake.

The rule nowEvery “My mistake” box comes from my mistakes log, or I confirm it myself. Facts on this site come from my log files, never from what probably happened.

A handoff is a note to a stranger

Before I leave a session, I type /handoff. It’s a command I built that writes one file of under 300 words with six headings: the goal, what’s done, the current state, the next steps with the first one kept small, open questions for me, and the 3 to 6 files to read first.

The new session then starts with one line:

The first message of a new session
Run /start, then read handoffs/2026-11-27-chapters-4-5.md and continue from the next steps.

The session that wrote this chapter started with a line like that. Its handoff file listed which chapters already exist and which stories they use, where the facts live, and which shell commands my guard blocks. I didn’t have to explain any of it, and that’s the test of a good handoff. Chapter 2 covers when to leave a chat and start fresh.

What a chat remembers goes stale

Files fix forgetting, but they can’t fix remembering wrong. On 26 November my agent kept adding work to merge requests I had already merged. In its context they were still open, because they were open when it last looked. Six commits ended up stranded on branches nobody would merge, and it sent me “PR READY” links for two merge requests I had already merged.

The fix is a habit. Anything a chat remembers about the world outside it is a snapshot, so before every upload and every “PR READY” line, my agent now checks the merge request on GitHub again.

The other kind of stale memory is a fix that never reaches the repository. When my guard stopped loading (chapter 3), the fix was a settings file at /home/user/.claude/settings.json, on the session’s temporary computer. It’s deleted with the session, so I’ve made the same fix three times. A fix that isn’t in the repository is a fix you’ll make again.

Try it yourself

Before you close your next session, paste this:

Your handoff prompt
Before I close this session, write a handoff file in a folder called handoffs/.
Name it with today's date and a short topic. Keep it under 300 words, with these headings:
Goal, Done, Current state, Next steps (the first one small), Open questions for me, Key files to read first.
Check on GitHub which pull requests are still open before you write the current state.
Save it on a branch and open a pull request.
Then give me one line to paste as the first message of the new session.

Merge the pull request before you start the new session, or the new session won’t see the file. Then add these lines to your instruction file, so the agent keeps the record and sticks to it:

Add to CLAUDE.md
Keep a mistakes log in logs/mistakes-log.md: one line per real mistake, with the date, what went wrong, why, and the rule that followed.
Never write that something happened unless it is in a file in this repository or I confirm it. If you can't find it, say so.
Before you act on anything you remember about GitHub, such as an open pull request, check it again.

Check yourself

A helper agent drafts a “lessons learned” section for your project. It reads well. What do you check before you use it?

That every event in it is in your files. An agent that can’t see what happened writes what usually happens, and that reads just as well as the truth.

Your fix works today, but it lives only on the session’s temporary computer. What happens tomorrow?

It’s deleted with the computer, and the problem comes back. Put the fix in the repository, or at least a check that catches the problem at the start of every session.

Your chat says a pull request is still open. That was true an hour ago. Can the agent add more work to it?

Only after it checks on GitHub. The chat remembers what it last saw. If you merged the pull request since then, new commits land on a branch nobody will merge.
