Chapter 1 · Set up

Set up once, then build by talking

The short list of things you need in place before Claude Code can build for you, what each one is for, and what breaks if you skip it. No coding needed.

26 November 2026 · 10 min read

The 30-second version

  • You need a paid Claude plan with Claude Code, a free GitHub account, and one private repository. That’s the whole shopping list.
  • The session’s computer is temporary. GitHub is where your work survives, so nothing counts until it’s saved there.
  • Claude works on a branch and asks to join main through a pull request. On a protected repository, your tap on Merge pull request is the only way in. On a free private one, nothing on GitHub enforces that, so you need your own guard.

Eight setup steps stand between you and the first time you build something just by describing it. I did them once, from an iPhone, and this website went live after 14 pull requests, each one merged by me.

When I started, words like “harness” and “repo” came at me fast, as if everyone already knew them. You need only a handful, and each one makes sense at the step where it starts to matter. Here are the steps in the order I’d do them again, with what breaks if you skip one. You don’t need to know how to code.

An unofficial guide, not made by or affiliated with Anthropic. I checked every step against the official docs on 26 November 2026. Screens change, so a button may have moved.

Step 1. Get a Claude plan that includes Claude Code

Claude Code in the browser and in the Claude app’s Code tab runs on Pro, Max, Ultra and Team plans, and on some Enterprise seats. The free plan isn’t on the list. The cloud computer it runs on has no separate charge, and its work counts towards your plan’s normal usage limit.

Two words matter from here on:

Model
= ClaudeThe AI that reads your message and decides what to do.
Harness
= Claude CodeThe program around the model. It opens files, runs commands, saves changes, and decides what the model is allowed to do.

More in the docs: how Claude Code works.

I learned what that second part means on 26 November, when the harness refused something I had already agreed to.

My mistake26 Nov 2026

My AI tried to raise its own permissions

My agent needed permission to install a tool, so it tried to write that permission for itself. The safety layer refused, twice, even though I had said yes. It was right: an AI shouldn’t loosen its own rules. So I added the rule myself on the GitHub website and saved it without looking. GitHub had picked the main branch, so the one file that controls what my AI may do skipped the review every other change gets.

The rule nowBefore saving anything on GitHub, choose Create a new branch. Changes to permissions get the most review, not the least.

One setting to check on day one: usage credits (once called extra usage), in Settings > Usage. I keep them off. Chapter 2 explains why.

Skip it and: there’s no Code tab, and nothing below works.

Step 2. Make a free GitHub account, and lock it

On 18 November, before I built anything, I couldn’t see why an AI app needed a second website. The answer is in two more words:

Session
= one conversation with Claude CodeIn the cloud it gets its own temporary computer. When the session goes quiet for a while, that computer is deleted.
GitHub
= where your project lives for goodClaude saves its work there before the computer goes, and the next session starts by copying it back.

Sign up at github.com (free). That same day I locked the account in three ways, and I’d recommend all of them:

  • Two-factor authentication with an authenticator app, with the recovery codes saved somewhere safe. Your GitHub account is about to hold everything your AI builds, so a stolen password alone shouldn’t be enough to get in.
  • Keep my email addresses private, in GitHub’s email settings. Every saved change carries an author, and with this on, GitHub uses a private no-reply address instead of your real one.
  • Block command line pushes that expose my email, just below it. If a tool ever tries to save a change under your real address, GitHub refuses it. Both settings matter the day you make anything public.

Skip it and: Claude’s work vanishes with each session’s computer. Cloud sessions need GitHub to copy your project in and to save it back.

Step 3. Create one private repository

On 25 November my agent tried to create a repository for me through GitHub’s API, and my own safety guard blocked it as a write it wasn’t allowed to make. The guard was right, and I made the repository myself. It’s a step I now always do by hand.

Repository
= a project folder that remembersAlso called a “repo”. It keeps every saved change, so you can see who changed what, and when, and go back (GitHub’s explanation).

Open github.com/new. Give it a short name, choose Private, and tick the option to add a README file. Claude Code’s docs say to start a new project this way, so the session has something to copy. Private first is my default: going public later is one switch, but once something is public, copies of it can exist outside your control.

Skip it and: Claude has nowhere to keep your work, and no place to read your rules from (step 8).

Step 4. Connect GitHub, and give Claude one repository only

On 18 November I gave Claude access to exactly one repository, my private hq, and added the website’s repository later that day, only once I needed it. If something goes wrong, it can only go wrong in the places you opened.

Go to claude.ai/code and follow the prompt to sign in with GitHub. That connection alone lets a session read public repositories. For a private one, you also install the Claude GitHub App on it. The onboarding offers this, or you can do it later from GitHub’s app page. When GitHub asks which repositories the app may use, choose Only select repositories and pick the one you just made.

Skip it and: your private repository doesn’t appear in the list when you start a session.

Step 5. Start a session and describe a task

On 21 November a session working on the website couldn’t see my to-do list, because the list lived in hq and a session only knows the repositories you picked when it started. Since then, anything a future session needs goes into a file in the right repository, never only into the chat.

In the Claude app’s Code tab (or at claude.ai/code), tap the repository selector below the message box and pick your repository. Then choose a permission mode. Plan makes Claude propose an approach and wait for your OK before it edits anything, while Accept edits and Auto let it get on with it. I’d start with Plan, because reading a plan teaches you how the agent thinks.

Then type what you want, in plain words, as you would to a colleague. Be specific: “add a page that lists my three favourite books” gets you further than “improve the site”, because Claude doesn’t have to guess what you meant.

Skip it and: there’s nothing to build.

Step 6. Let Claude work on a branch and open a pull request

Branch
= Claude’s own copy of your filesIt saves changes there in small steps, away from your main version (about branches).
Pull request
= “here are my changes, may they join main?”A page where you read every line, comment, ask for fixes, or close it without accepting anything (about pull requests).

By default, Claude works on a branch. Step 8 covers what actually stops it from touching main. When it reaches a stopping point, it pushes the branch to GitHub, and the session shows a Changes card with the lines added and removed, such as +42 -18. Tap the numbers to see what changed, then tap Create PR.

GitHub doesn’t notify you about pull requests you opened yourself, and Claude opens them under your account. So I had my agent end every message that needs me with one line, “PR READY”, and the link. I never go looking for them.

Skip it and: you have no checkpoint between the AI’s work and your live version.

Step 7. Review it, then press Merge pull request

Open the pull request in the GitHub app or in your browser. My routine on the phone takes three moves: read the plain-English summary at the top, tap Files changed if I want the detail, and tap Merge pull request if I’m happy.

On this website’s repository, nothing reaches main, and nothing goes public, until I tap that green button.

Merging is the step where you approve the work, so I never let the AI do it. My guard hook blocks it, and the final say stays with a person.

If you edit a file yourself on the GitHub website, check one thing before you save. The commit window picks main by default, so choose Create a new branch first. That default is how my permissions change skipped review (step 1).

Skip it and: the work sits on a branch forever, finished but not part of anything.

Step 8. Give it rules, then a wall

The model forgets everything between sessions. A file called CLAUDE.md at the top of your repository fixes that, because Claude Code reads it at the start of every session (how Claude remembers your project). Mine says things like “plan before building”, “work in small steps” and “never publish anything without asking”. If you don’t know where to begin, typing /init in a session drafts one for you. Keep it short, because every line is read in every session (chapter 2 has the numbers).

A written rule is still a request, and it depends on the model choosing to follow it. Claude Code can also run hooks, small scripts that check an action before it happens (hooks). Mine blocks pushes to main, force pushes and merges.

The last layer sits on GitHub itself. A ruleset refuses any change to main that doesn’t come through a pull request, whoever sends it, and on this website’s repository the list of people allowed to bypass it is empty, me included. GitHub’s free plan enforces rulesets only on public repositories. Chapter 3 covers how my hook and ruleset work together, and what I do for the private repositories that have no ruleset.

Skip it and: every session starts from zero, and “please don’t touch main” is only ever a polite request.

Try it: your first task

In a new session on your new repository, with the permission mode on Plan, paste this:

Your first message to Claude
Create a file called CLAUDE.md with three rules for you:
1. Before you change anything, write a short plan and wait for my OK.
2. Explain what you changed in plain English.
3. Never change main directly. Always use a branch and a pull request.

Approve the plan, tap Create PR, read the one file it added, and press Merge pull request. Then start a brand-new session and ask it what its rules are. It has never seen you before, and it will still answer with your three rules, because they now live in the repository instead of in a chat.

These rules are context, not a lock. The docs say there’s no guarantee of strict compliance, which is why step 8 adds a hook and a ruleset.

Check yourself

You closed the app last night, and the session’s computer was deleted. Is your work gone?

Not if Claude pushed it to GitHub. The next session copies the repository back in and carries on. Only work that never left the temporary computer is lost.

Claude has finished and the Changes card shows +12 −3. Has your project changed yet?

No. The changes are on a branch. Main only changes when you press Merge pull request.

You’re about to save an edit on the GitHub website. What do you check first?

That Create a new branch is selected. GitHub picks main by default, and then your change skips review.
