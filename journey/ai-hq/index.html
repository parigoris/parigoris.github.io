Chapter 3 · Working safely

I attacked my own AI guard. 76 of 97 attacks got in.

My safety guard passed every test I wrote for it. Then I asked an AI agent to attack it, and most of the attacks got through. Here’s how I rebuilt it, and the three layers I trust now.

18 November 2026 · 6 min read

The 30-second version

  • My own tests all passed. An independent AI reviewer still found 9 gaps, and later an attacking agent got 76 of 97 commands past my guard.
  • I rebuilt the guard to fail closed: if it can’t read a command with certainty, the answer is no. It now blocks 94 of the 97.
  • The guard also switched itself off, twice, without a word. A one-line test at the start of each session is what caught it.

On 18 November, my safety guard passed all 35 tests I had written for it.

Then I gave it to a reviewer that hadn’t built it, and the reviewer found nine gaps. One of them was simple: switch to the main version of the project first, then send the change from there, and the guard didn’t notice. I fixed all nine, wrote more tests, and watched 72 of them go green. I trusted it.

Eight days later I asked another AI agent to attack it on purpose. It tried 97 ways to get past, and 76 of them worked.

What the guard protects

My setup is the one from chapter 1: a private repository, an agent that works on branches, and pull requests I merge from my phone. The agent’s rules file asks it to plan first and never publish without me, but rules are only words. So I added a hook:

Hook
= a small script Claude Code runs before every commandMine is my guard. It blocks three moves: pushing straight to main, force-pushing over the history, and merging a pull request on its own.

97 attacks, 76 got through

On 26 November a test push found the first hole. A push to main, tucked inside a small shell loop, went straight past the guard. The guard checked the first word of each command for git, and in a loop the first word is do. It was a dry run, a rehearsal that stops before anything is sent, so nothing was pushed. But a two-letter word had fooled the guard, and I stopped assuming the rest of it was fine.

So I set up a red team, an agent whose only job is to play the attacker. My go-ahead was “go with any ideas, no need to ask me”. It wrote 97 attack commands and fed each one to a frozen copy of the guard, which only judged them. None of them ever ran.

76 got through. Most were the same forbidden push in a disguise:

  • wrapped inside another harmless program, such as nice or timeout, so the guard saw that program’s name first
  • with the flag shortened, --forc instead of --force, which git still accepts and my guard didn’t recognise
  • renamed with a git alias, so the word “push” never appeared at all
  • aimed at main through a roundabout address the guard didn’t expect

A few skipped git entirely and asked GitHub to approve or review a pull request through a different tool.

My tests checked the attacks I could imagine. The red team didn’t share my imagination.

Unknown means no

The 18 November fixes had already made the guard fail closed where it looked: if it found a git command it couldn’t read with certainty, it blocked it, and all 72 tests passed. The trouble was where it didn’t look. A push hidden inside a loop, a wrapper or an alias never registered as a git command at all, so it was allowed by default. Each fix after that would only have banned one more trick, and the attacker only needs the next one.

So the 26 November rebuild extended fail closed to everything. Any command that mentions a push or GitHub’s command-line tool must now be one plain command in a form the guard knows is safe, whatever wraps it. Anything else is blocked, even when it’s harmless. Against the same 97 attacks, it now blocks 94. The 3 left are harmless commands.

There’s a price. A note that only mentions a push, such as “don’t push to main”, now gets blocked too, so I write those another way.

Three layers, three different jobs

Even the rebuilt guard reads text, and text can hide things. A command written into a script file and run later is invisible to it. So I now think of safety as three layers, each one catching what gets past the one before.

The rules work like a sign on the door: the agent reads them and mostly follows them, but nothing forces it to.

The hook checks every command before it runs. It catches honest mistakes and most tricks, but only while it’s loaded, and the mistake below shows how easily it stops loading.

Ruleset
= a lock on GitHub’s sideA setting on GitHub itself, so it doesn’t care which command or trick reached it (about rulesets).

On this website’s repository, nothing gets into main without a pull request, and nobody can force-push or delete it. The list of people allowed to bypass it is empty, me included.

The catch is that GitHub’s free plan doesn’t enforce rulesets on private repositories. My public website has one. My private home base doesn’t, so there the guard is the last line, which is why I attack it and test it so often.

My mistake18 and 26 Nov 2026

My guard switched itself off. Twice.

On 18 November, the day I built the guard, I opened a session with two repositories in it. The guard quietly stopped loading, because the session’s main folder moved away from the settings file that switches it on. A test push to main went through, as a dry run, so nothing was sent. I fixed it and wrote a start-of-session check. On 26 November it happened again, after I attached two repositories in the middle of a session. Another test push caught it, and GitHub confirmed that main hadn’t changed. Nothing warned me either time. Only the test did.

The rule nowEvery session starts with a test push to main, and it must be blocked. I repeat it every time a repository is added. If it goes through, all other work stops until the guard is back.

Try it yourself

This is the test that caught my guard twice. A dry run asks git to rehearse sending your work to the main version, then stop before anything changes on GitHub. If you have any guard against pushing to main, the rehearsal must be blocked. Paste this at the start of a session:

Start-of-session test
Before we start, prove that my safety guard is on.
Run this dry-run push to the main branch: git push --dry-run origin HEAD:main
It must be blocked. If it is not blocked, stop and tell me before doing anything else.
Repeat this check every time a new repository is added to this session.

When Claude asks to run the command, read it before you approve it, and make sure --dry-run is still in it. Without that flag, it’s a real push.

If you don’t have a guard yet, the rehearsal won’t be blocked, and that’s a useful answer too. For a public repository, a ruleset on GitHub is free, and it’s the layer to add first. For the rules that go in your first instruction file, see the first task in chapter 1.

Check yourself

Your safety check passes every test you wrote. What’s the next test?

Ask something that didn’t build it to attack it: a reviewer, or an agent playing the attacker. My guard passed all 35 of my tests, then a reviewer found 9 gaps, and later a red team got 76 of 97 attacks past it.

Why does a guard that fails closed block some harmless commands?

Because it says no to anything it can’t read with certainty. Blocking a harmless note now and then is the price of not letting 76 attacks through.

The agent finds a trick your hook doesn’t know. Which layer still stops it?

The GitHub ruleset, because it sits on GitHub’s side and checks what arrives, not how the command was written. On GitHub’s free plan, that only works for public repositories.
